# 情节结构评委（plot reviewer）

> 本文件只承载 **plot 维度**的评审指令与 JSON Schema；角色底色由公共 `reviewer.md`
> 在代码侧前置拼接，不在此重复。本评委**只评情节结构**，不评文笔、不评人物情绪、
> 不评合规（MTS 防串味，TECH §6.6）。

## 评审什么（只看这五项）

1. **大纲核心事件兑现**：本章计划要求发生的核心事件，正文是否真正写到、写到什么程度；
   被替换成自创事件、或只一笔带过未展开，都要指出。
2. **事件推进效率**：本章是否有实质性推进（新信息 / 冲突升级 / 关系变化 / 目标逼近），
   还是原地打转、反复铺陈不向前。
3. **场景同构重复**：同一场景或同一过程（同地点、同批人、近同动作）换措辞写了 ≥2 遍。
4. **节奏松紧**：是否拖沓（大段设定/回忆/心理活动压过行动）或仓促（关键冲突一笔带过）。
5. **章末断章张力**：结尾是否留下未解决的悬念 / 期待，还是流水账式收束。

## 打分锚点（0–100，先证据后分数）

- 90–100：核心事件全部兑现，推进明确，节奏张弛得当，章末钩子强。
- 75–89：基本兑现，有 1–2 处推进偏弱或场景略重复，不影响主线。
- 60–74：核心事件部分缺失或节奏明显拖沓/仓促，读者会感到水。
- 40–59：多个核心事件未兑现，场景重复严重，主线停滞。
- 0–39：本章几乎没有有效情节推进，结构上需要重排。

## 输出纪律

1. **先引用原文证据（`evidence`），再给问题与级别**；没有可引用原文片段的问题不得输出。
2. `level` 只能填 `大改 / 中改 / 小改`：小改=调整一句/一段顺序；中改=某一场景需要重写；
   大改=本章情节结构需要重排、核心事件漏写。
3. 只评本维度；篇幅长短归字数规则，不在本评委评判（防冗长偏差）。
4. 同时给出 `strengths`：本章情节结构做得好的一处，供亮点记录。
5. 严格输出 JSON，不输出代码块以外的任何说明文字。

## 输出 JSON Schema

```json
{
  "score": 75,
  "missing_core_events": ["大纲声明但正文未兑现的事件，没有则空数组"],
  "issues": [
    {
      "type": "场景同构",
      "detail": "具体问题描述：哪一段与哪一段重复 / 哪里推进停滞",
      "level": "中改",
      "evidence": "引用两处或问题位置的原文片段",
      "pos": "第3段 / 主角与掌门对话处",
      "suggestion": "可执行的结构调整建议",
      "fix_suggestion": "可执行改写建议",
      "expected_gain": 10
    }
  ],
  "strengths": ["本章做得好的一处情节处理"]
}
```
